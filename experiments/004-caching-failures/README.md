# Experiment 004: Edge Caching, Coalescing, Failures & Network Degradation

## 1. Executive Summary & Research Questions

Stage 3 established routing policy behavior assuming every request the edge receives is forwarded upstream. Stage 4 asks what changes once the edge owns local state: can it serve a response itself, and what happens to timing, concurrency, and failure behavior once it can?

### Primary Research Question (004-A)
> With no cache at all, does every client request reach Origin exactly once, and does the edge treat a frequently-requested ("hot") key any differently from an infrequently-requested ("cold") one?

This is deliberately not an interesting question on its own — a No-Cache edge has no mechanism to differentiate keys. Its value is as the **fixed reference point** every later cache experiment in this stage gets compared against, under the identical workload.

---

## 2. Workload: The Hot/Cold Key Pattern

Every Stage 4 experiment that needs repeated-object traffic (004-A, and later the TTL, stampede, and coalescing experiments) uses the same generator, so results stay comparable across experiments:

- **1 hot key** (`/data/hot`), configured weight 8
- **8 cold keys** (`/data/cold-0` … `/data/cold-7`), weight 1 each
- Total weight 16 → the hot key receives ~50% of all traffic, each cold key ~6.25%

The sequence is generated by reusing Stage 3's `proxy.WeightedRoundRobinSelector` as a workload generator (`cmd/experiment-004a/main.go`, `keyWeights()`) — not a new implementation. Its smooth-interleaving property (proven exactly in `internal/proxy/weighted_round_robin_test.go`) is exactly what a realistic access pattern needs: it avoids the artificial burstiness a naive "repeat each key `weight` times" generator would produce (the same reasoning that motivated choosing smooth WRR for routing in the first place — see the Stage 3 README).

This required one small, reusable addition to shared infrastructure: `httpx.BenchmarkConfig` gained an optional `PathFunc func() string` field (`internal/httpx/benchmark.go`), called once per request to determine that request's path, overriding the static `Path` field when set. Tested directly in `internal/httpx/httpx_test.go` (`TestRunHTTPBenchmark_PathFunc`) against a real `httptest.Server` before being trusted in an experiment.

## 3. Results: Experiment 004-A — No-Cache Baseline

**Hypothesis (H1)**: see `hypotheses.md`. Topology: `Client -> Edge -> Origin`, no Proxy layer (routing/selection isn't what this stage's cache work is about, so it's a deliberate simplification, not an oversight). Origin has a 15ms artificial processing delay, representing real backend work — chosen specifically so a later cache hit's latency improvement will be visible and meaningful, not lost in noise. c=30, r=3000, single edge, single origin.

| Metric | Value |
|---|---:|
| Successful requests | 3000 / 3000 (0 failed) |
| Throughput | 1882.4 RPS |
| p50 | 15.67ms |
| p95 | 17.10ms |
| p99 | 18.62ms |
| Edge→Origin requests | 3000 |
| Edge→Origin requests == client successes | **true** |

### Findings

1. **Prediction 1 confirmed exactly**: 3000 client-successful requests produced exactly 3000 edge→origin requests. Every single request reached Origin — there is no code path in the current edge that could avoid this, which is exactly the point of establishing this now, before any cache exists to make the claim non-trivial.
2. **Prediction 2 confirmed**: p50 (15.67ms) sits almost exactly at Origin's configured 15ms delay, and the full p50→p99 spread is only about 3ms — tight and uniform. There is no visible hot/cold key distinction in the latency distribution, as expected: the edge has no mechanism yet to treat `/data/hot` any differently from `/data/cold-3`.
3. **`edge_origin_dials` reads 0 for the measured phase** — not a bug. The discarded warmup (30 requests, same concurrency) already dialed and pooled all 30 connections before the measured run's baseline snapshot was taken, so the entire 3000-request measured run ran on connections opened during warmup. Recorded here explicitly so it doesn't look like an unexplained anomaly later.

### Interpretation

This run does exactly what it was built to do: it's boring, and that's correct. The interesting question — how much of this upstream work and latency a cache eliminates — has no answer yet, because there's nothing to compare it against. That comparison is Experiment 004-A's second half, once `internal/topology`'s `EdgeServer` gains a TTL cache using the semantics decided before implementation (cache key = `method+path+query`, GET-only, 2xx-only, lazy expiration, no LRU/SWR yet — see the Stage 4 recon in the session record). Nothing about caching, coalescing, or failure behavior is claimed yet; this experiment's only job was to make sure the later claims have a real baseline to stand on.
