# Hypotheses: Experiment 004 — Edge Caching, Coalescing, Failures & Network Degradation

## H1 — No-Cache Baseline Characterization
Before any cache exists, the edge forwards every request to Origin regardless of how many times the same object has already been requested. Under a hot/cold key-access workload (one key receiving roughly half of all traffic, the remainder split across several cold keys), a No-Cache edge should show:

- *Prediction 1*: Upstream request count to Origin equals the number of successful client requests exactly — there is no mechanism by which a request could avoid reaching Origin.
- *Prediction 2*: Client-observed latency percentiles are dominated by Origin's own processing time (its configured artificial delay) plus network/dispatch overhead, and should be largely uniform across hot and cold keys — the No-Cache edge has no way to treat a "hot" key any differently from a "cold" one.
- *Purpose*: this run is not itself a finding — it exists to be the fixed reference point that the eventual TTL-cache run (same workload, same topology, only the edge's cache state differs) is compared against. Without a controlled No-Cache baseline, any later "caching helped" claim would have nothing rigorous to be measured against.

## H2 — TTL Cache Substantially Reduces Upstream Work and Improves Hot-Key Latency
Under the identical hot/cold key workload used for H1, an edge with a TTL cache (TTL configured longer than the whole run, so no mid-run expiry confounds this specific comparison — that is Experiment 004-C's question, not this one) should:

- *Prediction 1*: Reduce upstream (edge→origin) request count dramatically relative to the No-Cache baseline — most requests to any given key, after that key's first request, should be served from the edge without touching Origin at all.
- *Prediction 2*: Reduce p50 substantially, since the majority of requests become cache hits (no 15ms Origin round trip); p99 should be much less improved, since it's disproportionately made up of the unavoidable cache-miss requests (each of which still pays Origin's full processing time).
- *Explicit non-prediction*: this experiment does **not** predict the exact number of misses will equal the number of distinct keys (9). Under real concurrency, multiple requests for the same not-yet-cached key can race through before any of them completes and fills the cache — each of those races is itself a small, unplanned preview of the cache stampede Experiment 004-C studies directly. If observed, this should be reported as data, not treated as contamination to explain away.

## H3 — Synchronized Cache Expiry Produces a Real, Measurable Upstream Burst

Experiment 004-A already showed, unplanned, that concurrent *first-touch* requests to an empty cache can all miss before any of them fills it. This hypothesis asks the canonical, deliberate version of that question: what happens when a cache entry that *was* warm expires, and a burst of concurrent requests for that exact key arrives right after?

- *Setup*: a single hot key, cached and confirmed warm (one priming request), then its TTL is forced to elapse via `clock.MockClock` (deterministic — no reliance on real-time sleep windows), followed immediately by a burst of C concurrent requests for that same key, with C varied (10 / 30 / 100) to see how the effect scales.
- *Prediction 1*: without request coalescing (which does not exist yet), the number of upstream requests generated by the burst should approach C, not 1 — every concurrent miss independently fetches from Origin, because nothing currently prevents duplicate in-flight fetches for the same key.
- *Prediction 2*: peak concurrent Origin load (measured directly via `OriginServer.ConcurrencyStats`, new instrumentation this experiment needs and Stage 3 never did) should scale with C, and should be dramatically higher than the peak concurrent load a *primed, non-expired* cache produces under the identical burst (a deliberate control condition — the same C concurrent requests, same key, but hitting a cache that has NOT been expired, expected to generate ~0 upstream requests and ~0 peak Origin concurrency).
- *Prediction 3*: tail latency (p95/p99) during the stampede burst should be visibly worse than Origin's configured per-request delay alone, because Origin is now genuinely queueing/serializing C simultaneous requests rather than serving one request in isolation — this is a real queueing effect, not merely "C times the cost of one request," and should be reported as an observation with a Little's-Law-style interpretation (Stage 3's framing), not asserted as proven causality without checking.
- *Purpose*: this experiment exists specifically to produce the evidence that justifies building request coalescing (Experiment 004-D) — not to assume coalescing is needed and then look for numbers that support it.

## H4 — Request Coalescing Collapses a Stampede to One Upstream Fetch

Experiment 004-C confirmed the stampede is real and scales linearly with burst size. This hypothesis asks the direct question that motivates building coalescing at all: does deduplicating concurrent misses for the same key actually eliminate the wasted work, on the identical burst that just demonstrated the problem?

- *Setup*: 004-C's exact stampede cell (prime, confirm warm, force TTL past expiry via `clock.MockClock`, burst of C concurrent requests for the same key, C ∈ {10, 30, 100}) run twice per concurrency level on an otherwise-identical edge — once with coalescing left off (reproducing 004-C's own numbers as an in-experiment control) and once with `EdgeConfig.Coalesce` enabled — so coalescing is the only variable that changes between the two cells at a given C.
- *Prediction 1*: with coalescing enabled, upstream requests during the burst should be exactly 1 regardless of C — the first miss becomes the leader and fetches, every other concurrent miss for that key becomes a waiter and receives the leader's result without touching Origin.
- *Prediction 2*: Origin's peak concurrent load during the burst should drop to 1 (down from ≈C without coalescing) — the stampede's defining symptom (many simultaneous requests hitting Origin for one object) should disappear, not just shrink.
- *Prediction 3*: client-observed p99 during the coalesced burst should improve relative to the uncoalesced burst, though by how much is bounded by the same Origin-model limitation 004-C already flagged (Origin currently behaves closer to an infinite-server queue than a real, capacity-constrained backend) — a large p99 win here would be a genuine result, but a modest one would not falsify the case for coalescing, since 004-C already showed *why* p99 alone understates the stampede's real cost.
- *Explicit non-prediction*: this experiment does not claim coalescing is free. What it costs — one extra map lookup and mutex acquisition per request, and the correctness hazards documented directly in `cache.Coalescer`'s own doc comment (an abandoned in-flight entry blocking forever, a cancelled leader taking its waiters down with it) — is a design and implementation concern, not something this specific measurement run is built to quantify.

## H5 — Cache Insulates Warm Keys From an Origin Outage; Coalescing Fails Cleanly and Recovers on Cold Ones

004-C and 004-D both study *duplicate work* — the failure mode where Origin is healthy but gets hit more than it needs to be. This hypothesis asks the complementary, arguably more important question: what happens when Origin is not merely slow or momentarily overloaded, but genuinely down — a real `origin.Stop()`, connection refused, not a synthetic error returned from a test double?

- *Setup*: `Client -> Edge (cache + coalescing) -> Origin`. One key is primed and confirmed warm before the outage. Origin is then actually stopped (its listener closed — a real connection-refused failure any concurrent caller will hit, not a mocked one). While it is down: (a) repeated requests for the warm key, (b) a concurrent burst of requests for a different, never-cached key. Origin is then restarted on the exact same address (recovery), and both keys are checked once more.
- *Prediction 1*: every request for the already-warm key should keep succeeding throughout the outage, served entirely from the edge's cache — Origin being unreachable should be completely invisible to a caller asking for data the edge already has.
- *Prediction 2*: a concurrent burst against a key that was never cached should still coalesce into exactly one dial attempt to Origin, with the identical failure (502) shared by every caller in the burst — validating, under a real network failure rather than `coalesce_test.go`'s synthetic ones, that the failure-sharing behavior H4 assumed actually holds end-to-end.
- *Prediction 3*: the in-flight entry for that key must not be left stuck once the burst's failure completes — a fresh request for the same key, issued immediately after and still during the outage, should reach a fresh attempt (and fail again cleanly) rather than hang, directly exercising the "no abandoned in-flight entry" invariant `cache.Coalescer`'s doc comment names as the one that matters most.
- *Prediction 4*: once Origin is restarted, the previously-failing key should succeed on the very next request with no special recovery step needed — the system's state (an empty coalescer map, an empty cache entry for that key) should already be exactly what a normal cold fetch expects, because failed fetches were never cached and never left anything behind.
