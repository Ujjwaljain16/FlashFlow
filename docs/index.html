Why do routing
policies fail under load?

FlashFlow is a research laboratory, written in Go, for controlled experiments on distributed edge-routing behavior under heterogeneous conditions and finite serving capacity — six routing policies, two independent execution engines, sixteen development stages, each one's conclusion tested against its predecessor's.

Five stages narrowed or falsified the one before it. This is what survived.

EWMA — acute collapse (p99 4.40s) Round-robin — chronic collapse (p99 3.76s, 71% of run over capacity)

Real bucketed queue-depth data from a single seed of FlashFlow's canonical scenario — not illustrative. EWMA concentrates traffic 4.4× fair share, commits 97 requests to its target before reacting, spikes to a 95-deep queue, then fully recovers. Round-robin never concentrates enough to trigger any reaction at all — and, for exactly that reason, never drains either. Two different failure shapes, from two different causes.

The flagship scenario

Two failure shapes, not one spectrum

Five heterogeneous targets, capacity=1 each, a FlashCrowd workload peaking at t=2.5s, three independent seeds. Every policy in this scenario fails — just not the same way.

Acute over-commitment

EWMA and Adaptive build the deepest queues and show severe, often-non-draining collapse — committed backlog 93–127 for Adaptive, in every one of the three seeds, not just one.

Chronic under-provisioning

Round-robin shows a completely different failure: tiny committed backlog (4), but the highest fraction-of-time-over-capacity of all six policies (71%) — and it never drains either.

This is deliberately not framed as "Adaptive wins." Adaptive's own P99 was the worst of all six policies tested in this exact scenario, in every seed — a controlled ablation traced its resistance to collapse specifically to its Load signal, not general "smartness."

Where the boundary actually is

What this does not mean

The discipline this project holds itself to: every claim above is bounded, on purpose, in the same place the underlying research bounds it.

  • Scope — workload shapeCommitted backlog generalizes with perfect rank agreement across topology size (N=3/5/8); its cross-workload-shape generalization is real but imperfect.
  • Scope — real engineA validated real concurrency ceiling reproduces the mechanism's direction at most, not all, tested overload levels — it reverses at the most extreme level tested.
  • UnresolvedThe cache-affinity interim-latency effect (higher cache weight worsens interim latency, improves eventual recovery) was tested directly against this mechanism in two candidate locations and remains unexplained.
  • ReproducibilityVirtual-engine results are byte-for-byte reproducible given a seed, same machine and Go toolchain. The real engine is not byte-identical across reruns — genuine OS/timing variance, disclosed and measured, not hidden.
  • Not implementedLRU cache eviction, Doubly Robust off-policy evaluation, contextual bandits/RL, real tc netem, and OpenTelemetry are evaluated in planning and explicitly not built — see the scope freeze.

Under the hood

Two engines, one interface

A deterministic virtual-time simulator and a real net/http emulation engine both implement one shared, compile-time-verified ExperimentEngine interface — every experiment specification runs unmodified against either.

Virtual-time engine
A deterministic discrete-event simulator (internal/vtime, internal/replay). Byte-for-byte reproducible given the same seed, on the same machine and Go toolchain — confirmed directly, not assumed.
Real emulation engine
Real Go net/http servers and reverse proxy, with an in-process network-degradation simulator built in place of tc netem (Linux-only, unavailable on this project's Windows host). Subject to genuine OS scheduling noise — disclosed, not hidden.
Routing policies
Round-robin (no signal), weighted-round-robin (static weights), least-connections (in-flight count), EWMA (smoothed latency), P2C (sampled comparison), and Adaptive (a weighted combination of Load, Latency, Cache, and Cost).
Counterfactual replay
Two policies run against the byte-for-byte identical exogenous trace while each evolves its own isolated endogenous state — confirmed via full-trace identity/divergence tests, not summary statistics.
Cache & failure modeling
TTL caching with request coalescing and stale-while-revalidate. Failure injection via declarative YAML chaos schedules, backed by a 4-state health machine.
Statistics & tuning
Percentile, Mann-Whitney U, Cliff's Delta, and bootstrap confidence intervals, each checked against hand-computed references. Three tuners compared directly — Random Search wins on this project's own search space; the negative result was kept, not "fixed."
Diagnostic tooling
A CLI (flashflow report / explain / stress-map) and a live Control Room dashboard, both built on the completed research rather than extending it — reading, never recomputing, a stated finding.

Run it yourself

Every number above is reproducible

No account, no cloud dependency — clone the repo and Go 1.23 is the only requirement.

Full failure report for one policy against the canonical scenario
go run ./cmd/flashflow report --policy ewma
Read a report back as a causal narrative with counterfactual comparisons
go run ./cmd/flashflow explain <report.json> --policy ewma
Classify one policy across a 3×3 heterogeneity × workload grid
go run ./cmd/flashflow stress-map --policy least-connections
Launch the live Control Room dashboard (the chart above, interactive)
go run ./cmd/dashboard
